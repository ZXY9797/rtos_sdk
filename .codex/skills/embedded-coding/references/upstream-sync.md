# 上游同步与私有修复保护

用于 RTOS、驱动、HAL、CMSIS 或第三方源码的导入、更新与局部移植。
普通编码不需要执行同步流程。项目自己的迁移记录是事实来源；这里定义判断方法，
不保存某台机器的路径、旧 commit 或某块板的分类结论。

## 确定来源、范围和基点

从当前任务、仓库 remote、子模块/manifest、构建配置与现有 UPSTREAM 记录发现：

- 下游 SDK、上游主仓库、实际应用与构建目录。west 工作区根和 zephyr 主仓库是两个目录。
- 用户指定的 scope，以及源仓库、旧基点、目标 commit 的完整 SHA。
- 每个实际导入模块的来源 URL、独立基点、目标 revision、迁移目的路径。
  manifest 声明值与模块本地 HEAD 分别记录；本地 HEAD 不自动代表已迁移版本。

先检查上下游的 staged、unstaged、untracked 改动。已有脏改动不等于必须停工；
可在隔离目录生成候选差异，合并时保护用户内容。仅在缺失信息影响目标选择时询问。
“查看更新”只分析；“同步指定范围”可以在该范围内修改，不隐含提交、推送或升级其他模块。
需要最新上游时，确认 remote 后 fetch 对应 refs 并锁定 SHA，不把本地 HEAD 称为最新。

确认基点对象存在且祖先关系合理。来源曾重写历史、基点不明或有未登记回迁时，
先重建可验证的共同基线，不能猜一个版本后整文件覆盖。

## 先映射路径，再计算改动集合

用包含新增、删除、重命名的差异清单，例如：

```text
git diff --name-status -M <base_sha> <target_sha> -- <upstream_scope>
git log --oneline <base_sha>..<target_sha> -- <upstream_scope>
git show <base_sha>:<upstream_path>
```

自动解析时用 NUL 分隔形式并保留重命名前后路径，不按空格切割文件名。
建立显式的上游路径到下游路径映射；例如 Lark 项目可能采用
`include/zephyr/` → `include/lark/`、`Kconfig.zephyr` → `Kconfig.lark`。
映射规则要由当前树验证，不能推广到其他 SDK。

先映射，再匹配下游路径。不能仅取现有文件交集：新增头文件、Kconfig、CMake、
binding、链接段收集和生成器输入也可能是依赖。检查映射冲突以及大小写碰撞。
对上游删除/重命名，先检查本地扩展与调用者，不恢复下游有意裁剪的内容。

## 三方判断与分类

比较三份内容：经过已验证命名转换的上游旧基线、当前下游、经过同样转换的上游目标。
判断“只有命名差异”时，比较的是**旧基线与下游**；使用目标版本会混入尚未同步的改动。
分类记录只是线索，以当前 diff、有效修复记录和目录级架构约束交叉核验。

先摘出有效私有 bugfix 与架构分叉，再考虑自动更新：

| 类别 | 判据 | 处理 |
|---|---|---|
| E：有效私有修复 | 有触发条件、修复内容和验证判据，上游是否等效修复尚需核验 | 先评估修复，再合并；不得被 A/B 覆盖 |
| C：下游专属或有意删除 | 上游无对应实现，或裁剪是产品设计 | 保留；不要借更新恢复旧 API |
| D：实质分叉 | 驱动模型、API、构建接线或行为有本地变化 | 三方逐块吸收，保持既有契约 |
| A/B：未改或仅机械命名转换 | 归一化旧基线与下游一致，且没有 E/C/D 保护 | 导入目标变化并执行限定的命名转换 |
| 未知 | 记录缺失或证据冲突 | 读调用链和历史补分类，不能默认为 A/B |

目录级重构可以使整个驱动及其消费者成为 D 组；单文件表上的旧 A/E 标签不能覆盖
较新的架构事实。已经退役的修复记录不能被当成仍需重放的补丁。

对 D 组，在已授权同步范围内完成可确定的合并并展示候选 diff。
只有需要在不兼容的产品行为之间选择，且任务没有给出依据时，才把具体冲突交给用户。
不能仅因“本地有修改”而逐文件重复请求许可。

## 防止私有修复回归

对 E 组逐项核对目标版本的实际代码，不能仅凭 commit 标题或能编译判断已修：

1. 上游已有等效修复：核对调用路径、错误分支和回归判据，确认后退役本地补丁。
2. 上游未修：保留修复或移植到新实现，核对资源释放、唤醒和状态转换不变量。
3. 上游重写同一区域：按新架构重新验证触发条件，不能机械重放已失效的旧修复。

在项目已有的同步记录中保存适量证据：文件/符号、触发条件、本地修复、上游状态与核验 SHA、
验证方法和结果。历史故障是回归用例线索，不是当前故障的结论。

例如缓冲泄漏应覆盖失败回收、取消/关闭、再次提交和长期循环；增加缓冲数量只能改变
耗尽时刻，不能证明泄漏消失。代码检查与板上压测结果须分别报告。

## 转换与依赖闭合

只转换确认需要适配的路径、标识符、构建变量、DTS 属性及对应 C 宏。
保留版权、SPDX、真实 URL、第三方名称和确有兼容要求的协议字符串。
一行同时含 URL 与待转换代码时，按具体 token 处理，不跳过整行，也不全局盲替换。
转换应可重复执行而不继续改变结果；扫描残留并逐类解释合法保留项。

检查 `.c/.cc` 与头文件、Kconfig、CMake、DTS/binding、syscall 注册/生成物、链接脚本、
模块 revision 的依赖链。限制在用户 scope；若必要依赖跨出范围，先明确最小依赖差异，
再取得范围扩展的决定，不能静默扩大为全库同步。

## 验证与基点推进

按 [build-validation.md](build-validation.md) 检查构建与实际产物。
共享驱动/接口改动选择能覆盖受影响平台差异的配置；不硬编码两个示例板作为所有项目门槛。
复查新增、删除、改名、转换残留、私有补丁与最终文件范围。

只有某个基点所代表的导入范围都已完成处理，且验证达到该范围要求，才能推进它。
局部同步、跳过冲突或未完成验证时，保留全局基点，另记范围基点/已应用补丁和未处理项；
否则下次用新基点计算差异会漏掉尚未合并的更新。
每个 west/子模块单独记实际迁移 SHA，不能随主仓库一并写成各模块 HEAD。

最终交付包含范围与 SHA、采纳/保留/待处理的差异、私有修复状态及验证边界。
提交或推送只在用户要求时执行。
